# 確認済み
- 作業開始時の `git status --short` は出力なし。
- 指定された4資料はすべて存在する。
- `timerplan.md` の段階4候補は `CompiledOpnaPlayer.kt`、`PmdPerformanceState.kt`、`PmdSoftwareLfo.kt`、`PmdSoftwareEnvelope.kt`、`OpnaLikeSynthesizer.kt`。
- YM2608だけがタイマーBカウンターの桁あふれ、フラグ、IRQ通知を所有する。
- PMDはIRQ相当通知1回を演奏の1クロックとして消費する。PMD側にタイマー桁あふれ論理は置かない。
- PMD内部変数の数値回り込みは別概念で、段階4の時間通知には使わない。
- `t` / `T` は3資料内で初期説明と訂正版が矛盾する。明示的な訂正版である洗練版の「`t` は2分音符基準テンポ、`T` はタイマーB直接値」を採用するが、段階4では構文を変更しない。
- `CompiledOpnaTimeline` は初期値と曲中変更を `TIMER_B` 大域イベントとして音符・状態より先に並べる。
- `CompiledOpnaPlayer.handleTimelineEvent` は現在 `TIMER_B` を処理していない。
- `OpnaTimerB` は物理側でフレーム別通知回数を事前確保し、`prepare` と消費APIを提供する。
- 通常LFOと通常包絡は現在、各インスタンスのBPM由来サンプル位相で製品経路中に進む。
- 固定・拡張約56Hzも同じ `advanceSample` 内にあるため、通常側だけを通知駆動へ分離する。
- 明示的リセット、巻き戻し、再生器切替、製品ループ境界は再生器状態と音源状態を同時に初期化する。
- 直接 `OpnaSequencer` 経路は活動中だが段階4では変更しない。
- 変更許可一覧は `CompiledOpnaPlayer.kt`、`PmdPerformanceState.kt`、`PmdSoftwareLfo.kt`、`PmdSoftwareEnvelope.kt`。
- 再生器は物理タイマーBを区間ごとに準備し、消費済み通知回数を事前確保配列でPMD状態へ渡す。
- 時刻0の全大域イベントを処理してから初回区間でタイマーを読み込み開始するため、同時刻の最終プリセットが初周期に使われる。
- 実行中の `TIMER_B` 変更は再読み込みラッチだけを更新し、進行中の物理周期を捨てない。
- 通常LFO・通常包絡は通知回数だけ進み、固定・拡張約56Hzは従来のサンプル位相を維持する。
- 包絡の現在値出力、クロック進行、リリース完了印、物理停止の順序を維持する。
- 実装差分に禁止された依存、コレクション演算、ラムダ、コルーチン、三角関数はない。
- 共有メタデータ、Android共有エンジン、アプリKotlinのコンパイルは成功した。
- 既存のOPNA高頻度経路監査はビルド依存として合格した。
- 本番差分は許可した4ファイルだけで、バイナリ、生成物、外部素材はない。

# 棄却
- `timerplan.md` のYM2608オーバーフロー論理を、そのままPMDソフトウェア論理として採用すること。ユーザーが誤りと明示しているため。
- タイマーB通知2回をPMD内部1クロックへ分周する案。指定資料では通知1回がPMDの1クロックである。
- PMD状態にオーバーフローカウンターやフラグを追加する案。ハードウェア責務を越境するため。
